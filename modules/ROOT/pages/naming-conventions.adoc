= Naming Conventions and Reuse

Use a generic name for internal endpoints and message types instead of referencing the associated EDI format, version, and document type. Follow the examples in the table for Target at Host and Source at Host message types naming conventions.

[%header%autowidth.spread]
|===
|Message Type or Endpoint |Flow Example |Recommended Naming |Not Recommended Naming |Reasoning
|Target at Host Message Type |X12 4010 850 |in-tgt-purchase-order |4010-850-json |Future proofs your naming conventions so that when you receive purchase orders from other partners who use different X12 versions, EDIFACT, or non-EDI formats, your message type names give you better context when they are mapped to the same target message type.
|Source at Host Message Type |JSON |out-ar-invoice | 5010-810-json |Since the same internal JSON format is mapped to other X12 versions, EDIFACT, XML, or JSON based on the message type your partner chooses, use a name that references the application, such as order, order-ack, invoice, or ship-notice instead of referencing the EDI format or message type that was used by the first trading partner you onboarded.
|Target at Host Endpoint | |HTTP-Target-PurchaseOrder-Proc-API |HTTP-Target-850-JSON-Endpoint |Recommended when sending a translated inbound purchase order to a backend process API.
|AS2 Receive from Partners Endpoint |AS2-Receive-from-partners-Generic |AS2-Receive-X12-5010-850-from-[Your First Partner’s Name] |Since you’ll reuse the same endpoint to receive data from many other partners as you expand the usage of Partner Manager, use a generic name for this endpoint type, instead naming the endpoint after the first partner you onboard.
|===

== HTTP Receive from Partners Endpoints

When creating HTTP Receive from Partners endpoints from host or partner profiles:

* Use a generic name for the host profile.
* Reuse the same endpoint for multiple partners and message types.
